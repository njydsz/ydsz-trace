# Ydsz Trace 后续版本迭代优化建议

> 对标行业主流竞品（ELK、Loki、Graylog、阿里云 SLS、腾讯云 CLS、Splunk、Datadog Logs）与互联网大厂研发规范，结合当前仓库现状输出可落地的迭代建议。
> 时间：2026-08-09 ｜ 评估范围：`logs` / `logc` / `pkg` / `web` 全模块。

---

## 一、现状盘点（Code Review 结论）

在给出建议前，先客观定位当前仓库的真实状态。**亮点**：纯 Go 单文件顺序读取 17.8GB 日志约 33 秒、简洁的 Client-Server 架构、统一 API 响应封装、SSE 流式搜索与实时跟踪、登录速率限制、Prometheus 指标、SQLite WAL 自动建表、密码加盐哈希等，功能骨架完整。

但存在一批**与当前文档描述不一致、以及距离生产级仍有差距**的问题，直接影响后续迭代质量，需优先处置。

### 1.1 文档与实现严重漂移（会误导二次开发）

| 项 | 文档/配置声称 | 代码实际情况 | 影响 |
|---|---|---|---|
| 数据库 | README 声称 "兼容 MySQL 和 PostgreSQL"，快速开始引用 `sqls/mysql.sql`、`sqls/postgresql.sql` | 已迁移到 **SQLite**（`logs/models/def.go` 用 `modernc.org/sqlite`），只有 `sqls/sqlite.sql` | 新人按 README 部署必然失败 |
| docker-compose | 环境变量为 `YDSZ_DB_PATH`，但配置示例仍停留在 MySQL 时代 | 代码确实用 `YDSZ_DB_PATH`（SQLite 路径） | compose 与 README 口径混杂 |
| API 参考 | `POST /logs/stream` 描述为 "SSE 流式搜索进度推送"，未说明 zip 下载链路 | `Stream` 只推进度与汇总，不真正回传 zip | 接口契约不明确 |
| 配置项 | README 列 `sqlhost/sqlport/sqluser/sqlpwd/database` | `logs/conf/app.conf` 实际用 `dbpath/temppath`，SQL 配置已废弃 | 配置文档过期 |
| 权限模型 | 无说明 | 仅单一 admin 账号，无角色/多用户 | 安全边界单薄 |

**处置**：这一项不属"新功能"，但应作为迭代 0 的文档修正任务先落地，否则后续所有优化都会在错误的文档基础上进行。

### 1.2 工程化基础设施缺失（对标大厂研发规范差距最大）

- **无 CI/CD**：仓库没有 `.github/workflows/`（`make ci` 目标存在但无实际流水线），README 的 CI 说明为空头支票。
- **无静态代码分析**：`make lint` 仅 `go vet`；未接入 `golangci-lint`、`staticcheck`、`govulncheck`（漏洞扫描）。
- **后端测试覆盖单一**：虽有 16 个 `_test.go`，但集中在 `pkg` 工具层与 `logc/file`；**`logs` 服务端核心业务（client/item/logs 控制器、鉴权、会话）几乎没有集成测试**，`logs/e2e` 与 `pkg/integration` 未见稳定断言。
- **前端工程化完全空白**：无 ESLint、无 TypeScript、无 vitest/jest、无 i18n、无 Pinia，`lint`/`test` 脚本是占位 `echo`。
- **无版本管理**：README 提到 `dev` 分支接受 PR，但仓库只有 `main`，无 PR/MR 模板、无 changelog、无语义化发布。

### 1.3 安全短板（生产阻断级）

- **`vkey`（客户端密钥）明文展示**：`web/src/views/Clients.vue` 表格中直接渲染 `vkey` 列，任何登录用户可见，且前端拿到密钥可自行伪造客户端。
- **破坏性操作走 GET**：`/client/delete`、`/item/delete`、`/client/changeStatus`、`/item/changeStatus` 均为 `GET`，非幂等且易触发 CSRF / 预取/爬虫误删。
- **密码哈希算法偏弱**：`pkg/auth/password.go` 用 `SHA-256 + salt`（快速哈希），README 自己也标注应迁移 `bcrypt`/`argon2id`。虽然比明文好，但 SHA-256 对 GPU 暴力破解没有抗性。
- **弱默认口令**：`logs/conf/app.conf` 默认密码 `change_me_production`、logc 默认密钥 `123456`，文档也明示需改——但无启动强制校验。
- **会话内存态**：`pkg/session` 基于进程内 `map`，重启即丢、多副本不共享，且 `Secure` Cookie 在无 TLS 时无法生效。
- **`extractClientIP` 直接信任 `X-Forwarded-For` 首值**：若前面无可信代理，攻击者可伪造 IP 绕过登录限流。
- **前端 `localStorage` 存用户名做登录态**：`web/src/store/auth.js` 仅凭 username 存在即视为已登录，可被轻易伪造展示为已登录。

### 1.4 功能与体验短板（对标 SLS / Loki / Datadog Logs）

- **搜索结果仅整包 zip 下载，无在线分页浏览**：`LogSearch` 命中后前端只能下载 zip，无法在网页内翻页/高亮/排序查看——这是与商业日志平台体验差距最大的一点。
- **检索能力有限**：仅"包含匹配 + 简单正则 + 5 级 level 过滤 + 行内时间范围"，无布尔组合、无字段级过滤、无聚合统计、无二次检索、无历史检索任务持久化（仅有前端 10 条 localStorage 历史）。
- **大文件检索为全量扫描**：每次 `ReadString` 都从头扫整个文件，无索引/无分片/无并行分块读取，客户端多、文件大时服务端要反复读同一文件。
- **日志采集仍是"按需拉取"**：非实时推送/订阅，`tail` 依赖 500ms 轮询；无日志轮转（logrotate）感知、无多文件通配（`*.log`）采集、无压缩归档管理。
- **无告警/订阅**：命中 ERROR/关键字无法触发通知（SLS、Datadog 的告警是核心卖点）。
- **无多租户/权限隔离**：所有客户端、日志项对单一 admin 全可见，无法按项目/团队划分可见性。
- **SSE 前端实现有 bug**：`LogTail.vue` 里 `eventSource` 是死代码（实际用 fetch 手写解析），`stopTail` 关的是 null 引用，流未被真正 `reader.cancel()`，且 dev 代理路径 `/api/logs/tail` 与 vite proxy 的 `/logs` 不匹配，本地开发会 404。
- **可观测性指标为自研手写**：未用 `prometheus/client_golang` 标准 SDK，缺少 histogram 分位数、过程序生命周期统计、`/metrics` 自身请求也被 HTTP 指标计数造成轻微污染。

## 二、迭代路线图（按优先级分四阶段落地）

以下建议按 **"先止血 → 再补基础 → 后追功能 → 终做平台"** 排序，每阶段给出可验收目标，避免一次性大而全导致搁浅。

### Phase 0：一致性修复与安全止血（≈ 1 个迭代，建议 1–2 周）

> 目的：让文档、部署、基础安全与代码对齐，消除生产阻断项。这一阶段不引入新架构，只做"纠偏"。

1. **文档同步**：README 全面改为 SQLite 单库，删除 MySQL/PG 描述；修正配置表（`dbpath/temppath/runmode` 等）；补全 `/logs/stream`、`/logs/tail` 接口契约（请求/响应/SSE 事件格式）。`docker-compose.yml` 与 `sqls/` 保持口径一致。
2. **破坏性接口改为 POST + CSRF 防护**：`client/delete`、`item/delete`、`changeStatus` 一律从 `GET` 改为 `POST`；评估引入 CSRF token 或依赖 `SameSite=Strict`（当前是 Lax）+ 校验自定义请求头。
3. **前端隐藏 `vkey`**：`Clients.vue` 中 `vkey` 不再渲染为明文列，仅显示脱敏（如 `******`）或"已设置"，编辑时留空表示不变更。
4. **密码哈希升级为 Argon2id**：替换 `pkg/auth` 实现（`golang.org/x/crypto/argon2`），保留旧格式校验与平滑迁移（登录成功自动重哈希落库/落配置）。`password_test.go` 同步覆盖。
5. **强制生产环境安全前置检查**：启动时若检测 `runmode=prod` 且密码/密钥仍为默认值，则 `log.Fatalf` 拒绝启动并提示配置环境变量。
6. **修复 `LogTail` SSE**：删死代码 `eventSource`，改用 `AbortController` 在卸载时真正 `reader.cancel()`；修正 dev 代理 `/logs` 路径。

**验收**：`make ci` 可通过（若 Phase 1 未建 CI，则本阶段以 `make test && make lint` 通过 + 手工回归登录/增删改查为验收）；README 无 SQLite 之外的陈旧描述；默认口令无法在 prod 模式启动。

---

### Phase 1：工程化基础设施（≈ 1–2 个迭代，建议 2–4 周）

> 目的：补上大厂研发规范的核心底座，让后续迭代可控、可回归、可追溯。这是长期价值最大、但往往被忽略的部分。

1. **建立 GitHub Actions CI 流水线**：`push`/`PR` 触发，串联 `golangci-lint` + `go vet` + `go build` + `go test -race`（三个 module 各自跑）+ `govulncheck` + 前端 `npm ci && npm run build`；发布 tag 时自动打镜像。
2. **接入 `golangci-lint`**（`staticcheck`/`errcheck`/`gosec`/`revive` 等），替换现有 `go vet`；产出 `.golangci.yml`。
3. **补充后端核心测试**：为 `logs` 的 `client`/`item`/`logs` 控制器、`admin.Login` 鉴权与限流、`session` 增补单元 + httptest 集成测试；为 `logc` 的 `ReadString`（大文件/正则/时间范围）补性能与正确性基准。
4. **前端工程化最小集**：接入 ESLint + Prettier（先跑通 `npm run lint`），引入 vitest 至少覆盖 `auth.js`、`logs.js` 等纯逻辑与 API 层；将手写 reactive store 迁移到 Pinia（便于测试与 SSR 安全）。
5. **引入语义化版本 + Changelog**：为打 tag 提供 `vX.Y.Z` 约定，仓库加 `CHANGELOG.md`，PR 模板含"是否破坏兼容/是否需迁移"。

**验收**：`.github/workflows/ci.yml` 绿；`npm run lint`/`npm run test:unit` 非占位；核心控制器有测试；`go test -race ./...` 三个 module 全绿。

---

### Phase 2：检索能力与在线体验（≈ 2–3 个迭代，建议 4–6 周）

> 目的：把"下载 zip 再本地翻"升级为"网页内即时浏览"，直追 SLS/Loki 的在线检索体验。这是产品价值提升最关键的一环。

1. **在线分页浏览命中结果**：`logs` 服务端新增 `POST /logs/search` 返回命中行（分页 + 排序），前端 `LogSearch` 在表格内高亮关键字、上下翻页、导出当前页/全部；保留原 zip 下载为"导出"功能。为此需在 `logc` 侧返回带行号/时间戳的结构化命中，而非仅 zip。
2. **分片并行读取 + 内存限量**：将大文件按固定块（如 64MB）切分，多 goroutine 并行匹配后归并排序，避免单线程全量扫描；对命中结果设置行数上限（如单节点最多 10 万行），防止 OOM。
3. **布尔检索与字段级过滤**：`key` 支持 `AND/OR/NOT` 组合（可做简单表达式解析，或退化为多关键词分组），并支持按常见字段（如 `client`、`level`、`traceId`、`requestId`）过滤。
4. **检索任务持久化**：新增 `t_task` 表记录"检索会话"（参数、进度、结果 zip 路径、创建人/时间），前端可查看历史检索并复用参数；`stream` 进度与任务表关联。
5. **日志采集增强**：`logc` 增加多文件通配（`/path/**/*.log`）、logrotate 感知（重命名后继续读新文件）、可选 gzip 压缩传输。
6. **告警/订阅 MVP**：新增"日志告警规则"（项目 + 关键字/正则 + 级别 + 时间窗 + 触发次数），命中后发 webhook（钉钉/企业微信/邮件）。优先 webhook，成本低、见效快。

**验收**：网页内能对 17.8GB 级文件分页浏览命中并高亮；布尔检索可用；历史检索可回放；演示一条 webhook 告警。

---

### Phase 3：架构健壮性与可扩展（≈ 2–3 个迭代，建议 4–8 周）

> 目的：解决单点、多副本、与更大规模采集的架构瓶颈，为横向扩展铺路。

1. **会话/限流外置**：`session` 与登录限流从进程内存迁移到 Redis（引入 `go-redis`，提供内存实现作为单机 fallback），支持多副本部署。
2. **`logs` 无状态化**：SQLite 单文件数据库对多副本不友好。按部署规模二选一：
   - 中大规模：引入 **PostgreSQL**（复用现有 `sqlx`，抽象存储层，`t_client/t_item/t_task` 均可上 PG）；
   - 单机轻量：保持 SQLite，但将 DB 挂到共享卷，明确"单副本"约束并写入部署文档。
   （注意：README 已删除的 MySQL/PG 支持若近期不打算恢复，应彻底清理旧 SQL 与配置残留。）
3. **认证升级**：从"Cookie Session"演进为可选 **JWT（Access + Refresh）** 双 token（`pkg/auth/jwt.go` 现为死代码，正好可激活），支持 API 密钥/Agent 令牌鉴权，为告警 webhook 回调和第三方集成打底。
4. **观测性标准化**：接入 `prometheus/client_golang`，用 Histogram 统计检索耗时分位数、采集延迟、并发扫描数；为 `logs`/`logc` 补充结构化日志（`log/slog`），带 `traceId`/`client` 关联。
5. **配置与密钥管理**：支持 `YDSZ_*` 环境变量集中化 + 可选 `.env`/K8s Secret 注入；移除代码内散落的默认密钥。

**验收**：多副本 `logs` 部署会话共享；结构搜索在千级节点/百 GB 级别仍可用；`/metrics` 为标准 Prometheus 格式含 histogram。

---

### Phase 4：平台化与差异化（可选 / 长期）

> 目的：在满足基础之上做出差异化竞争力（对标大厂但更轻量、更适合内网）。

- **多租户 + RBAC**：项目/团队维度隔离客户端与日志可见性，支持多管理员角色。
- **日志上下文一键定位**：命中行可"一键跳到 tail 该文件该时刻"，打通检索与实时跟踪。
- **Trace/异常聚合**：识别 `traceId` 串，做跨节点调用链聚合与异常聚类（对错误日志按堆栈相似度分组）。
- **插件化数据源**：抽象 `Reader` 接口，支持接入标准文件、Docker/k8s 日志、systemd journal 等。

## 四、落地建议（一次性推进的注意事项）

1. **先定 CI 再动功能**：Phase 0/1 若不同步建 CI，后续重构无回归护栏，极易在改存储层时悄悄引入回归。
2. **存储层抽象先行**：如果 Phase 3 计划支持 PG，建议在 Phase 2 检索任务持久化时就按"接口化存储"设计 `t_task` 写入，避免二次改造。
3. **性能基准随读随跑**：`logc/file` 已有性能类测试雏形，建议维护 `bench` 用例（17.8GB 读取 + 分片并行），作为 Phase 2 分片优化的回归基线。
4. **前端改动小步走**：LogSearch 的在线浏览涉及后端新接口 + 前端大改，建议后端接口先行、前端灰度（保留旧 zip 下载），避免一次替换造成可用性回退。
5. **安全优先合并**：Phase 0 的安全项（vkey、GET→POST、Argon2id、默认口令）建议按独立 commit 逐个合入，每个都有对应测试与回滚方案。
