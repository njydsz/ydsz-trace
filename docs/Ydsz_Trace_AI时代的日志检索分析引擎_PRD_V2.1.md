## 一、项目背景与现状

### 1.1 现有项目概况

Ydsz Trace v1.x 是一款基于 Go 语言开发的轻量级高性能分布式日志追踪检索系统，定位为"比 grep 快、比 ELK 轻、比 Loki 更适合内网"。系统采用简洁的 Client-Server 架构：在每台目标服务器部署 logc 客户端代理（默认端口 2020）读取本机日志文件，由 logs 集中管理服务端（默认端口 2021，Gin 框架 + 内置 SQLite）统一调度，并通过内置 Vue 3 + Vite 构建的 SPA 控制台提供交互入口。仓库按 Go Workspace 多模块组织，pkg 为跨模块共享库，sqls 存放 SQLite 初始化脚本；支持本地源码运行（make run-logs / make run-logc）与 Docker Compose 一键部署。

v1.x 已具备的能力是本次升级的地基，必须在演进中被继承而非推翻：

| 能力域 | v1.x 现状 | 升级态度 |
|--------|-----------|----------|
| 极致性能 | 纯 Go 编写，单线程读取 17.8GB 日志文件约 33 秒 | 继承并强化（列式 + 下推） |
| 分布式架构 | 每台服务器部署 logc Agent，Web 控制台集中管理 | 继承，增强配置下发与自治 |
| 灵活检索 | 关键字检索、正则匹配、级别过滤、时间范围、上下文行数控制 | 继承，升级为统一 DSL |
| 实时追踪 | SSE 流式推送新增日志行，单/多节点合并跟踪 | 继承，增强模板级过滤与回放 |
| 流式进度 | 多客户端并发搜索时 SSE 上报各节点进度与结果 | 继承 |
| 零依赖存储 | 内置 SQLite（modernc.org/sqlite 纯 Go 驱动 + WAL 模式） | 演进为列式段存储 + SQLite 存元数据 |
| 管理控制台 | 内置 Vue 3 + Vite + Element Plus + Tailwind CSS 的 SPA | 继承，重构为对话式工作台 |
| 安全加固 | 加盐密码哈希、登录速率限制、HttpOnly Cookie 会话、路径穿越防护、正则 ReDoS 防护 | 继承并补齐脱敏与租户隔离 |
| 可观测性 | Prometheus metrics 端点（QPS/延迟/在线数/内存） | 继承并扩展到 AI 链路指标 |

### 1.3 现状痛点与瓶颈

v1.x 在"单机、小数据量、已知关键词"的场景下体验优秀，但在真实生产环境（多服务、日增百 GB、故障未知）中暴露出八个结构性瓶颈：

检索范式停留在 grep 时代：强依赖用户预先知道精确的关键词。拼写差异、大小写、参数变化、中英文混排都会导致漏检，更无法表达"最近系统有什么不对劲"这类开放性意图。

日志始终是非结构化文本行：没有字段，无法按 status、user_id、latency 做过滤、聚合、分组与下钻，无法回答"哪个接口错误最多"这类统计型问题。

SQLite 面向事务而非分析：行数过亿后全文匹配与聚合性能急剧退化；缺少列式压缩，原始文本存储成本高；单点写入存在天花板，且分析查询会拖慢在线写入。

结果过载、噪音淹没信号：一次查询返回十万行，重复堆栈占据 90% 以上篇幅，用户被迫人肉去重，真正关键的异常行往往被淹没。

完全被动式：只有人主动来问才有输出。系统不会主动发现"出现了一种从未见过的错误"，也不会在错误率突增时主动告知。

缺少链路视角：日志之间没有 TraceID 串联，跨服务定位只能靠人工比对时间戳，微服务场景下定位成本极高。

上下文割裂：日志与指标、链路、变更记录（发布、配置、扩容）相互脱节，导致"知道报错但不知道为什么"成为常态。

零 AI 能力：没有语义理解、没有自然语言查询、没有自动归因、没有摘要，与 AI 时代用户对"问答式运维"的预期存在代差。

### 1.4 竞品与技术趋势对标

AI 时代的日志引擎正在被两股力量重塑：一是以 ClickHouse / DuckDB 为代表的低成本高压缩分析型存储，二是大模型带来的语义理解与推理能力。对标结论如下：

| 方案 | 检索范式 | 存储成本 | 智能化 | 内网私有化 | 运维复杂度 | 本产品机会点 |
|------|----------|----------|--------|-----------|-----------|-------------|
| ELK / OpenSearch | 倒排 + DSL | 高（索引膨胀） | 弱（需外挂） | 可 | 高（重） | 以 1/10 资源达到 80% 能力 |
| Grafana Loki | 标签 + 行过滤 | 中（对象存储） | 弱 | 可 | 中 | 补齐结构化与语义层 |
| ClickHouse 自建 | SQL OLAP | 低（压缩强） | 弱（需外挂） | 可 | 中 | 在其之上加 AI 语义层 |
| Splunk / Datadog | SPL + AI 助手 | 极高（授权费） | 强 | 难（SaaS） | 低（托管） | 内网可私有化的平替 |
| 新兴 AI 日志工具 | 自然语言优先 | 中 | 强 | 多为 SaaS | 低 | 数据不出内网的差异化 |
| Ydsz Trace v2 | 自然语言 + DSL 双模 | 低（列式压缩） | 强（内建） | 完全支持 | 低（单二进制） | 轻量 + 智能 + 私有化 |

## 二、AI 时代日志引擎的范式转变

### 2.1 六个根本性转变

日志系统的本质任务从未改变：在最短时间内，用最少的人力，回答"系统发生了什么、为什么、怎么办"。改变的只是达成路径。AI 带来的不是"给旧系统加一个聊天框"，而是六个层面的范式重写：

| 维度 | 传统 / v1.x 形态 | AI 时代形态 | 对产品的意义 |
|------|-----------------|-------------|-------------|
| 查询入口 | 关键词、正则表达式 | 自然语言意图 + 可执行 DSL 回显 | 用户不再需要学习查询语法 |
| 数据组织 | 以原始行为单位存储 | 模板化 + 聚类的"语义压缩层" | 让海量日志进入模型上下文成为可能 |
| 召回方式 | 倒排匹配 / 顺序扫描 | BM25 + 向量 + 结构化 + 时间的混合召回 + Rerank | 从"匹配字面"到"匹配意思" |
| 交互形态 | 一次一查的表单 | 多轮诊断会话（Agent，携带证据链） | 从查询工具变为排障同事 |
| 系统角色 | 被动响应查询 | 主动观察：检测 → 归因 → 告警 → 报告 | 从"人找日志"到"日志找人" |
| 结果呈现 | 日志流水列表 | 结论 + 证据 + 建议 + 可下钻原文 | 人读结论，机器读日志 |

### 2.2 第一性原理：上下文预算决定架构

本 PRD 的全部架构决策，都源于一个硬约束：大模型的上下文窗口是有限的、昂贵的，而日志是无限的、廉价的。因此 AI 日志引擎的核心不是"把日志喂给模型"，而是先让日志变少、变结构化、变可索引，再让模型只看压缩后的精华。

价值密度定律：10 亿行日志中真正承载信息量的通常不足 1000 行。AI 引擎的核心 KPI 不是存储了多少，而是压缩掉了多少、又发现了多少。

由此推导出本产品的核心架构思想——智能漏斗（Intelligence Funnel），即按单位成本从低到高分为四层，只有经过前一层严格剪枝后仍无法解决的少数问题，才交由下一层处理：

| 层级 | 手段 | 单位成本 | 处理数据量级 | 典型任务 | 是否必须 |
|------|------|----------|-------------|---------|---------|
| L0 规则层 | 正则、模板匹配、字段过滤 | ≈0（毫秒级） | 全量原始行 | 解析、过滤、采样、屏蔽 | 永远在线 |
| L1 统计层 | 基线、突变检测、TopN 聚合 | 极低（纯计算） | 聚合后的模式计数 | 异常发现、趋势、噪音识别 | 永远在线 |
| L2 嵌入层 | 向量化、聚类、相似检索 | 低（可纯 CPU） | 模板级（万级） | 语义检索、聚类摘要、去重 | 默认开启 |
| L3 生成层 | 大模型推理与 Agent | 高（Token / GPU） | 百级样本与摘要 | NL2DSL、根因推理、报告生成 | 按需触发 |

### 2.3 产品设计原则

智能漏斗优先：能用规则与统计解决的，绝不调用模型；模型只处理被前三层剪枝后的极少数据。

语义压缩先行：先聚类去重，再送入模型；模型看到的是"3000 个模式"而非"1000 万行原文"。

证据可追溯：AI 的每一个结论必须携带可点回原文的证据引用，禁止无据推断，禁止编造堆栈与代码。

私有化优先、云端可选、可完全离线：默认所有 AI 能力本地化；云端为可选项；断网时自动降级为 L0+L1+L2，核心检索能力不受影响。

不牺牲 v1.x 的核心竞争力：轻、快、零外部依赖仍是第一卖点，AI 是增量而非负担，单二进制部署形态必须保留。

渐进可关：每一个 AI 能力独立开关、独立降级路径、独立成本预算，任何一项故障都不影响日志检索主链路。

评测驱动上线：每个 AI 功能必须配套评测集与量化门槛，不达标不上线（详见第 6.6 节）。

人机协同与反馈回流：AI 输出假设，人做决策；人的每一次纠正都要能沉淀为规则、样本或 Few-shot 案例。

接口标准化优先：参照字节跳动《后端对外接口规范》与阿里《Java 开发手册》REST API 规范，v2 接口一律统一响应格式、统一错误码、统一版本管理，避免当前 v1 双风格并存的隐患。

## 三、产品目标与成功指标

### 3.1 目标用户与核心场景

| 角色 | 核心诉求 | 高频场景 | 对应能力 |
|------|----------|---------|---------|
| 一线开发 / SRE | 线上出问题时快速定位 | 报错排查、灰度验证、发布后盯屏 | NL 查询、Live Tail、根因 Agent |
| 研发负责人 / 架构师 | 掌握系统健康度与趋势 | 日报周报、容量与稳定性复盘 | 洞察看板、异常时间线、事故简报 |
| 测试工程师 | 定位失败用例的根因 | 自动化失败归因、环境差异比对 | TraceID 链路、时间窗对比 |
| 运维 / 交付 | 低成本部署与稳定运营 | 多环境纳管、权限与配额、升级 | Agent 集中管理、脱敏、成本治理 |
| 安全 / 合规 | 可审计、数据不出内网 | 敏感信息检查、访问审计 | 脱敏规则、审计日志、私有化部署 |

### 3.2 关键用户故事

US-1（零关键词排障）：凌晨订单服务告警，值班同学打开控制台直接问"订单服务过去一小时为什么报错变多"，系统在 30 秒内给出结论：某模板错误量在 02:14 突增 47 倍，集中在 pod-7，首个错误出现在发布后 3 分钟，并附 5 条原文证据与一条链路。

US-2（语义找相似）：开发拿到一条没见过的 NullPointerException，选择"找相似日志"，系统跨服务返回历史上出现过的 3 类相似异常及其当时的处理结论。

US-3（主动发现）：系统在没有任何查询的情况下，于 09:23 推送"检测到 1 个全新错误模板，过去 10 分钟出现 214 次，疑似与 09:15 的配置变更相关"，并支持一键发起 AI 诊断。

US-4（链路还原）：客服反馈某订单支付失败，输入订单号，系统按 TraceID 还原跨 6 个服务的调用链，标出耗时最长与首个报错的 span，并联动展示对应日志。

US-5（对话式追问）：在诊断会话中连续追问"影响多少用户""和上周比呢""给我一份事故简报"，系统基于同一上下文持续作答并生成可分享的 Markdown 报告。

US-6（老用户无感迁移）：v1.x 用户升级后，原有关键字检索、级别过滤、多节点 Live Tail 的用法与快捷键完全保留，AI 能力作为可选项出现。

### 3.3 量化目标

北极星指标：故障平均定位时长（MTTI）下降 60%，且 50% 以上的排障会话无需用户手工输入关键词。

| 指标 | v1.x 基线 | v2 目标 | 口径说明 |
|------|-----------|---------|---------|
| 故障平均定位时长 MTTI | 约 30 分钟 | ≤ 12 分钟 | 从告警触发到给出可执行结论的中位数 |
| 零关键词排障占比 | 0% | ≥ 50% | 会话中用户未手工输入正则/精确关键词的比例 |
| 日志模板解析准确率 | 无 | ≥ 95% | 5000 行人工标注集上模板边界与参数槽正确率 |
| 语义压缩比 | 1 : 1 | ≥ 50 : 1 | 原始行数 : 聚类后的模式数（同服务同期） |
| NL 转 DSL 准确率 | 无 | ≥ 90% | 200 条中英文问句评测集，执行结果等价为正确 |
| 异常检测召回率 | 无 | ≥ 80% | 20 例注入故障演练中成功告警的比例 |
| 异常检测误报率 | 无 | ≤ 10% | 告警事件中人工判定为无效的比例 |
| 根因命中率 | 无 | ≥ 60% | 30 例真实事故复盘中根因方向与复盘结论一致 |
| 存储压缩比 | 1 : 1（原始文本） | ≥ 8 : 1 | 列式 + zstd 后的磁盘占用对比 |
| 单会话 LLM 成本 | 无 | ≤ 0.05 元 / ≤ 8k Token | 本地部署计为 0，云端模式下的 P95 |

### 3.4 明确不做（Non-Goals）

不做全量采样的通用 APM：v2 仍以日志为主体，链路能力从日志中重建，不引入独立的全量链路采集与存储体系。

不做 SIEM / 安全审计产品线：不提供合规报表、威胁情报、UEBA 等安全专业能力。

不做商业化多租户 SaaS：v2 面向内网私有化部署，租户隔离仅做到团队/项目级。

不替代指标系统：不自建时序数据库，Prometheus 等指标系统通过接口联动。

不自研大模型：模型层全部通过适配层对接开源或云端模型，保持可替换。

## 四、总体架构设计

### 4.1 逻辑架构分层

v2 在保留 v1.x Client-Server 骨架的前提下，将单体服务端拆为七层。所有 AI 能力集中在"语义层"，通过适配层与上下游解耦，可整体关闭而不影响主链路。

```
┌──────────────────────────────────────────────────────────────┐
│ 6 应用与交互层  Vue3 SPA：对话工作台 / 经典检索 / 洞察看板 / 链路 / 告警 / 管理 │
├──────────────────────────────────────────────────────────────┤
│ 7 开放层        REST API · gRPC · SDK(Go/Java/Python) · MCP Server · Webhook │
├──────────────────────────────────────────────────────────────┤
│ 5 查询服务层    统一 DSL 解析 · NL2DSL · 混合检索(RRF) · 聚合下推 · 结果缓存 │
├──────────────────────────────────────────────────────────────┤
│ 4 语义层(AI)    Parser · Embedding · Cluster · Anomaly · LLM Gateway · Agent │
│                 └─ 模型适配：本地(gguf/vLLM/Ollama) ⇄ 云端 API ⇄ 规则兜底   │
├──────────────────────────────────────────────────────────────┤
│ 3 存储索引层    列式 Segment(zstd) · 倒排+BM25 · 向量(HNSW) · 模式时序计数表 │
├──────────────────────────────────────────────────────────────┤
│ 2 传输层        HTTP/2 批量上行 · 背压 · 断点续传 · 本地磁盘队列             │
├──────────────────────────────────────────────────────────────┤
│ 1 采集接入层    logc Agent：文件 tail · journald · 容器 stdout · Syslog · OTLP │
└──────────────────────────────────────────────────────────────┘
```

三条主链路：

写入链路：采集 → 多行合并 → 模板匹配与字段抽取 → 本地轻量索引 → 批量上行 → 服务端解析补全 → 写入列式 Segment + 更新倒排 + 更新模式时序计数 →（异步）向量化与异常检测。

检索链路：NL / DSL 输入 → 查询计划 → 时间分片裁剪 + 模板 ID 前置过滤 → 下推至相关 Agent 本地索引 → 服务端合并排序（RRF + Rerank）→ 聚类折叠 → 返回并高亮证据。

智能分析链路：模式时序表 → 异常检测（L1）→ 生成候选异常集 → 聚类摘要（L2/L3）→ 触发告警或用户提问 → Agent 多轮工具调用（L3）→ 结论 + 证据 + 建议 → 反馈回流。

### 4.2 部署形态（三档）

| 档位 | 适用场景 | 存储 | AI 能力 | 最低资源 | 形态 |
|------|----------|------|---------|---------|------|
| L 轻量档 | 单机 / 小团队 / 边缘节点 | 内置 SQLite + 本地段文件 | 仅 L0 规则 + L1 统计（AI 全关） | 2C4G | 单二进制 |
| S 标准档 | 中小集群（≤ 200 节点） | DuckDB / 单机 ClickHouse | 本地嵌入 + 本地 7B 或云端 LLM | 8C16G | Compose / K8s |
| E 企业档 | 大型内网 / 强合规 | ClickHouse 集群 + 对象存储冷层 | 全本地 GPU（vLLM + bge-m3 + 14B/32B） | 16C64G + GPU | K8s / 专有云 |

强制要求：三档使用同一份二进制与同一套配置格式，仅通过配置项切换；L 档在完全断网、零模型文件的环境下必须 100% 可用。

### 4.3 与 v1.x 的模块改造映射

| v1.x 模块 | v2 变化 | 兼容性策略 |
|-----------|---------|------------|

## 六、AI 能力专项设计

### 6.1 模型选型矩阵

模型层通过统一适配层（aimodel）接入，支持本地进程内推理（gguf / llama.cpp）、本地服务（Ollama / vLLM）、云端 API 三种形态，同一能力可热切换，互不绑定厂商。

| 能力 | 本地首选 | 云端备选 | 资源要求 | 调用频率 | 说明 |
|------|----------|----------|---------|---------|------|
| 日志解析规则生成 | Qwen2.5-7B-Instruct | 云端通用模型 | CPU 可跑，GPU 更快 | 低频（新格式首次） | 离线生成规则，在线零调用 |
| 文本向量化 | bge-m3 / gte-Qwen2-1.5B | 云端 Embedding | CPU 1-2 核，约 2GB | 高频（增量） | 中文强，支持多语言 |
| 结果重排 Rerank | bge-reranker-v2-m3 | — | CPU / GPU 均可 | 中频（可选开关） | 默认关闭，命中率不足时开启 |
| 聚类摘要与命名 | Qwen2.5-7B-Instruct | 云端通用模型 | CPU 可跑 | 中频（模板增量） | 结果缓存，同模板只算一次 |
| NL 转 DSL | Qwen2.5-7B / 14B + 约束解码 | 云端通用模型 | GPU 建议，CPU 可降级 | 高频（每次查询） | 输出必须是合法 DSL，失败即降级 |
| 根因推理 Agent | Qwen2.5-14B / 32B | 云端强推理模型 | 16GB+ 显存 | 低频（按需） | 受步数与 Token 预算约束 |
| 规则与统计兜底 | —（无模型） | — | 0 | 永远在线 | 断网、超预算、模型故障时兜底 |

### 6.2 三级路由与降级策略

第一级 本地优先：默认所有 AI 能力走本地模型；本地模型缺失或推理超时（默认 10s）时进入第二级。

第二级 云端可选：仅在管理员显式开启并配置密钥后可用；外发前必须执行脱敏，且只发送模板与采样样本，不允许整段原始日志出网。

第三级 规则兜底：任一级失败均自动降级为关键词 + 结构化过滤 + 统计排序，并在结果区明确标注"AI 能力已降级，当前为关键词结果"。

强制约束：日志检索主链路（FR-4）不得依赖任何模型；模型全不可用时，系统基础可用性为 100%。

### 6.3 成本控制策略

| 成本项 | 控制手段 | 目标 |
|------|---------|------|
| 向量化 | 只做模板级而非逐行；模板去重后向量规模可控；历史模板懒加载 | 10 万模板约 400MB 向量，CPU 可承载 |
| 聚类摘要 | 同模板摘要永久缓存；仅对新增或变更后模板调用；批量合并请求 | 摘要调用量下降 90% 以上 |
| NL 转 DSL | 使用 7B 小模型 + 约束解码；相同问句结果缓存（TTL 5 分钟） | 单次 ≤ 1.5k Token，命中缓存免调用 |
| 根因推理 | 严格剪枝：先由 L1 异常检测锁定候选集，再交模型；输入只含聚类摘要 + Top N 样本 | 单次输入 ≤ 6k Token |
| 上下文压缩 | 超预算时自动收敛时间窗、提升聚类粒度、减少样本条数后重试一次 | 压缩后仍无法放入则转统计结论 |
| 配额治理 | 按用户 / 会话 / 日 三级 Token 预算，超限降级并计入审计 | 单会话 ≤ 8k Token（云端模式） |

### 6.4 Agent 工具集定义

根因 Agent 采用 ReAct 式多步推理，每步调用一个工具并观察结果。工具均为只读，禁止任何写操作与命令执行。

| 工具名 | 入参 | 用途 | 输出约束 |
|--------|------|------|---------|
| search_logs | DSL 查询串、条数上限 | 按条件检索原始日志 | 默认 ≤ 50 条，含证据引用 ID |
| agg_stats | 维度、指标、时间窗 | 按模板/服务/级别聚合计数与趋势 | 只返回聚合值，不返回原文 |
| get_context | 日志 ID、前后行数 | 取命中行的上下文 | ≤ 200 行 |
| list_templates | 服务、时间窗、排序 | 列出高频或新增模板 | ≤ 100 个模板 |
| get_anomalies | 时间窗、严重度 | 取异常检测事件 | 含突变倍数与基线值 |
| get_trace | TraceID | 取链路与 span | 含耗时与错误标记 |
| diff_time_window | 两个时间窗、维度 | 对比两个时段的差异 | 只输出差异 Top N |
| query_metrics | 指标名、时间窗 | 查询外部指标系统（可选） | 仅当配置了指标源时可用 |
| search_runbook | 关键词 | 检索运维手册与历史案例库 | 返回片段与来源链接 |

### 6.5 隐私与数据安全

默认数据不出内网：本地部署下所有模型推理在服务端完成，无任何外网请求。

外发双闸门：启用云端模型必须同时满足"管理员授权"与"字段脱敏前置"两个条件，缺一不可。

脱敏规则内置手机号、身份证、银行卡、邮箱、JWT、密码、密钥等类别，支持自定义正则与字段白名单；展示脱敏与外发脱敏分离配置。

外发内容最小化：仅发送模板串、聚合数值与不超过 20 条的采样样本，禁止发送完整日志段与用户数据全集。

全链路审计：AI 会话的每一次输入、工具调用、输出均留痕，可回溯可导出。

### 6.6 AI 效果评测体系

AI 功能一律以评测集为上线门禁，评测失败即阻断发布。评测集随真实使用与人工纠正持续扩充。

| 能力 | 评测集 | 核心指标 | 上线门槛 | 回归方式 |
|------|--------|---------|---------|---------|
| 日志解析 | 5000 行人工标注日志 | 模板准确率、参数槽 F1 | 准确率 ≥ 95% | 每次模板算法变更触发 |
| NL 转 DSL | 200 条中英文问句 | 执行结果等价准确率 | ≥ 90% | CI 每次构建运行 |
| 语义检索 | 100 组相似日志对 | Top10 命中率 | ≥ 85% | 模型或索引变更触发 |
| 聚类摘要 | 200 个模板人工评分 | 可读性、准确性 5 分制 | 均分 ≥ 4.0 | Prompt 变更触发 |
| 异常检测 | 20 例注入故障演练 | 召回率、误报率、发现时延 | 召回 ≥ 80%，误报 ≤ 10% | 阈值或算法变更触发 |

| Agent 常驻内存 | ≤ 50 MB | 单 Agent，默认配置 |
| 轻量档整机资源 | ≤ 2C4G | AI 全关，50 节点规模 |

| 指标项 | 目标值 | 测试条件 |

### 8.2 可用性与可靠性

服务端无单点：标准档及以上支持查询节点多副本；写入节点故障时 Agent 本地缓存补传。

AI 能力故障隔离：语义层任何组件崩溃不影响写入与检索主链路，健康检查 30 秒内判定并切换降级。

数据可靠性：写入确认前落盘，异常退出不丢已确认数据；支持按段校验与修复。

升级可靠性：支持滚动升级与版本回退，v1 Agent 与 v2 服务端可长期混跑。

### 8.3 安全

继承 v1 安全能力：加盐密码哈希（Argon2id）、登录速率限制、HttpOnly Cookie 会话、路径穿越防护、正则 ReDoS 防护。

新增：字段级脱敏、外发白名单、AI 会话审计、模型密钥加密存储（不得明文落配置）。

传输安全：Agent 与服务端之间支持 mTLS；云端模型调用强制 HTTPS。

权限最小化：Agent 只具备日志读取权限，不提供任何远程命令执行能力。

**V2.1 新增安全要求**：

| 安全项 | 要求 | 验证方式 |

### 8.4 兼容性与可维护性

协议兼容：v1 的注册、心跳、查询、追踪接口在 v2 中以 /api/v1 保留至少一个大版本。

配置兼容：沿用 INI 配置 + 环境变量覆盖机制，新增项均有默认值。

可维护性：配置项集中声明、默认值内建、启动自检（-check）输出配置与健康状态。

可观测性：扩展 Prometheus 指标，新增 AI 调用量、Token 消耗、模型延迟、异常事件数、向量索引规模等指标。

## 九、关键接口设计概要（V2.1 增强版）

### 9.1 查询 DSL 示例

```
-- 例 1：NL 生成的可读 DSL
service = "order-svc" AND level IN (ERROR, FATAL)
  AND ts BETWEEN now()-1h AND now()
| SEARCH "timeout"
| GROUP BY template_id ORDER BY count DESC LIMIT 20

-- 例 2：语义检索
service = "pay-svc" | SEMANTIC "支付回调重复提交导致幂等失败" TOPK 20

-- 例 3：聚合下钻
level = ERROR AND ts BETWEEN now()-24h AND now()
| STATS count() BY service, bin(ts, 5m)
| HAVING count > 100
```

### 9.2 统一响应格式（V2.1 强制规范）

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "trace_id": "abc123",
  "pagination": {
    "page": 1,
    "page_size": 20,
    "total": 156
  }
}
```

约束：
- code 为数字类型，0 表示成功，非 0 为错误码
- v1 接口返回格式保持不变（兼容性），v2 接口统一使用上述结构
- 前端解包层统一处理，不分散在各 API 文件中判断

### 9.3 核心 REST API

| 方法 | 路径 | 用途 | 版本 |
|------|------|------|------|
| POST | /api/v2/query | 执行 DSL 查询，返回聚类折叠结果 | v2 |
| POST | /api/v2/query/nl | 自然语言查询，返回 DSL + 解释卡 + 结果 | v2 |
| POST | /api/v2/semantic/search | 语义相似检索 | v2 |
| GET | /api/v2/patterns | 模板列表、趋势、新增标记 | v2 |
| GET | /api/v2/anomalies | 异常事件列表与详情 | v2 |
| POST | /api/v2/conversations | 创建诊断会话；/messages 追加追问 | v2 |
| GET | /api/v2/traces/{trace_id} | 链路与 span 详情 | v2 |
| GET | /api/v2/tail (SSE) | 实时日志追踪 | v1 兼容 + v2 增强 |
| GET | /api/v1/* | v1 检索与节点管理能力 | 保留 |
| GET | /metrics | Prometheus 指标（含 AI 指标） | v1 兼容 |

### 9.4 MCP Server 工具暴露

v2 以 MCP 协议暴露只读能力，使 IDE 与其他 Agent 可直接调用：list_services、query_logs、search_similar、get_patterns、get_anomalies、start_diagnosis。所有调用继承调用方的数据权限与脱敏策略。
