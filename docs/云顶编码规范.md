## 一、总则

### 1.1 规范定位

本规范是云顶追踪项目的**强制性编码公约**，覆盖 Go 后端与 Vue 3 前端全栈。条款按三级约束力度标注：

- **【强制】** 违反将导致代码评审不通过（CR Block），CI 门禁拦截
- **【建议】** 推荐遵守，评审时作为改进项提出
- **【参考】** 提供范式指导，允许根据场景变通

### 1.2 核心原则

| 原则 | 说明 |
|------|------|
| **可读性优先** | 代码是写给人看的，机器只是恰好能执行它 |
| **最小惊讶** | API 命名与行为一致，不产生歧义 |
| **防御性编程** | 所有外部输入不可信，所有错误必须处理 |
| **单一职责** | 一个函数/结构体/文件只做一件事 |
| **一致性压倒个性** | 项目已有约定优先于个人偏好 |

### 1.3 工程价值观

1. **从"比 grep 快"到"让日志自己说话"** — 代码服务于 AI 化排障定位
2. **安全性不可妥协** — 密码哈希、CSRF 防护、参数校验是底线而非选项
3. **数据不出内网** — AI 默认本地化；云端外发必须前置脱敏
4. **智能漏斗优先** — 能用 L0 规则与 L1 统计解决的，不调用模型
5. **可观测性内建** — 日志、Metrics、Tracing、AI 链路指标是功能的一部分
6. **评测驱动上线** — 每个 AI 功能必须配套评测集与量化门槛
7. **渐进式演进** — 先跑通、再跑快、最后跑优雅

```
│   ├── session/         #    会话存储（内存/Redis）

│   ├── source/          #    日志源抽象（File/Docker/K8s/OTLP）
│   ├── logmerger/       #    日志合并
│   ├── schema/          #    v2.0 数据模型定义

│   ├── controllers/    #    控制层（按业务域分包）
```

### 2.2 模块依赖规则

```
【强制】依赖方向只能自上而下：

    logs ──→ pkg ←── logc
     │               │
     └──── 互不可依赖 ──┘

    logv ──→ logs API（HTTP 调用）
```

- `pkg` 不得依赖 `logs` 或 `logc`
- `logs` 与 `logc` 不得相互依赖
- 前端通过 HTTP API 与服务端交互，禁止直接引用 Go 模块

### 2.3 目录职责边界

| 目录 | 职责 | 禁止行为 |
|------|------|---------|
| `controllers/` | 请求解析、业务编排、调用 models | 不得包含 SQL 拼接逻辑 |
| `models/` | 数据库 CRUD + 数据迁移 | 不得调用 controllers 或 gin 上下文 |
| `routers/` | 路由注册 + 中间件链配置 | 不得包含业务逻辑 |
| `pkg/` | 跨模块可复用工具 | 不得引入业务特定逻辑 |
| `logv/src/views/` | 页面渲染 + 交互 | 不得直接操作后端数据源 |
| `logv/src/api/` | HTTP 请求封装 | 不得包含 UI 渲染逻辑 |

## 三、命名规范

### 3.1 Go 命名

#### 3.1.1 包命名

```
【强制】
- 全小写，无下划线、无数字开头
- 使用单数形式（用 ratelimit 而非 rate_limits）
- 包名应与其目录名一致
- 避免使用 util、common、misc 等无意义包名（已在项目中的允许保留）
```

示例：
```go
package ratelimit   // ✓
package ratelimits  // ✗（复数）
package rateLimit   // ✗（驼峰）
package util        // △（已有项目保留，新增避免）
```

#### 3.1.2 文件命名

```
【强制】
- 使用 snake_case：file_source.go、docker_source.go
- 测试文件统一 _test.go 后缀：file_source_test.go
- 文件名应直接反映其内容主体
- 单文件不超过 800 行，超出时拆分
```

#### 3.1.3 类型命名

```
【强制】
- 结构体使用 UpperCamelCase（PascalCase）
- 数据库映射结构体以 T 前缀标识：TClient、TItem、TTask
- 接口以 er/able/ior 结尾：Source、Backend、Limiter
- 请求/响应结构体以 Req/Resp/DTO 后缀：LogsReq、SearchResp
- 错误类型以 Error 结尾：statusError
```

示例：
```go
type TClient struct { ... }         // 数据库表结构
type Source interface { ... }       // 日志源接口  
type LogsReq struct { ... }         // 请求体
type TailResp struct { ... }        // 响应体
```

#### 3.1.4 函数与方法命名

```
【强制】
- 使用 lowerCamelCase
- 公开函数必须有注释（以函数名开头）
- CRUD 动词统一：Add / Get / Update / Delete / Query / List
- Boolean 返回值以 Is/Has/Can/Should 开头
- Get 与 Query 区分：Get 返回单条（不存在返回 error），Query 返回切片（不存在返回空切片）

【建议】
- 构造函数以 New 开头
- 工厂方法以 New + 具体类型
```

违例：
```go
func getClient(id int64) (TClient, error) {}      // ✗ 应改为 GetClient
func Query_All_Client() []TClient {}                // ✗ 应改为 QueryAllClients
func IsUserExist() bool {}                          // △ 建议改为 Exists
```

#### 3.1.5 变量与常量命名

```
【强制】
- 局部变量：简短且有意义（err、cfg、db、srv）
- 常量：UPPER_SNAKE_CASE：MaxRetries、DefaultTimeout
- 缩写词保持大小写一致：URL、HTTP、ID（不写 Url、Http、Id）
- 避免单字母变量（循环计数器 i/j/k、坐标 x/y 除外）
```

#### 3.1.6 JSON Tag 与 DB Tag

```
【强制】
- JSON tag 使用 lowerCamelCase：sourceType、createdTime、taskNo
- DB tag 使用 snake_case：source_type、created_time、task_no
- 字段重命名必须同步更新两个 tag，保持映射关系

【建议】
- 时间字段统一命名为 CreatedTime / UpdatedTime（JSON: createdTime / updatedTime）
- 布尔字段统一命名为 IsXXX / EnableXXX（JSON: isXxx / enableXxx）
```

### 3.2 前端（Vue 3 + JavaScript）命名

#### 3.2.1 文件与目录

```
【强制】
- 组件文件使用 PascalCase：Login.vue、LogSearch.vue、TraceView.vue
- 工具/服务文件使用 camelCase：http.js、auth.js、formatDate.js
- API 模块按业务域拆分：logs.js、client.js、item.js、alert.js
- 单文件不超过 600 行
```

#### 3.2.2 组件命名

```
【强制】
- 组件名使用 PascalCase，DOM 模板中可连字符使用
- defineComponent 的 name 属性与文件名一致
- 布局组件前缀 Layout：Layout.vue、LayoutHeader.vue
- 业务组件避免语义化过重的命名，保持中立
```

#### 3.2.3 变量与函数

```
【强制】
- 变量、函数：lowerCamelCase
- 常量：UPPER_SNAKE_CASE：STORAGE_KEY、API_BASE_URL
- 组合式函数以 use 前缀：useAuth()、useLogSearch()
- 事件处理函数以 handle 前缀：handleLogin()、handleSearch()
```

#### 3.2.4 路由命名

```
【强制】
- 路由 name 使用 camelCase：logSearch、logTail、traceView
- URL path 使用 kebab-case（如需要）：/log-search、/log-tail
- meta 字段统一：{ public: true, title: 'xxx', icon: 'xxx' }
```

### 4.1 Go 代码格式

```
【强制】
- 使用 gofmt / goimports 格式化（make fmt 自动执行）
- 缩进使用 Tab（Go 官方标准）
- 行宽不超过 120 字符

```

```
【强制】
```

## 五、注释规范

### 5.1 注释原则

```
【强制】
- 所有公开函数/类型/常量必须有 GoDoc 格式注释（以名称开头）
- 注释使用中文（项目已有约定），保持与代码同步
- 注释描述"为什么"而非"做什么"（做什么由代码自身表达）
- 禁止注释掉的代码进入版本控制（应删除或通过 git 历史追溯）

【建议】
- 复杂算法需要添加实现思路说明
- 安全相关操作需要注释说明防护目的
- TODO/FIXME/HACK 标注统一格式：// TODO(author): 说明 — YYYY-MM-DD
```

### 5.2 GoDoc 注释示例

```go
// AddClient 注册一个新的日志采集客户端。
// 如果 IP+Port 组合已存在，返回已存在记录的 ID 而非重复插入。
// 返回 0 和 error 表示数据库操作失败。
func AddClient(ip string, port int) (int64, error) {
    // ...
}

// TClient 映射 t_client 表结构，记录日志采集节点信息。
type TClient struct {
    ID        int64     `json:"id" db:"id"`
    IP        string    `json:"ip" db:"ip"`
    Port      int       `json:"port" db:"port"`
    CreatedAt string    `json:"createdAt" db:"created_at"`
}
```

### 5.3 前端注释

```javascript
/**
 * 全局 Axios 实例
 * - baseURL: 相对路径（同域部署）
 * - timeout: 120s（适配日志检索长耗时场景）
 * - withCredentials: true（支持 HttpOnly Cookie 会话）
 */
const http = axios.create({ /* ... */ })

/**
 * 非安全请求附加 X-Requested-With 头
 * 用于 CSRF 防护：浏览器 CORS 策略阻止第三方站点设置该头
 */
http.interceptors.request.use(config => {
    if (!['get', 'head', 'options'].includes(config.method)) {
        config.headers['X-Requested-With'] = 'XMLHttpRequest'
    }
    return config
})
```

## 六、错误处理规范

### 6.1 Go 错误处理

```
【强制】
- 所有错误必须处理，不得使用 _ 忽略（除非有明确注释说明原因）
- 错误包装使用 fmt.Errorf + %w：fmt.Errorf("add client: %w", err)
- 底层错误向上传播时添加上下文信息
- 不二次包装哨兵错误：errors.Is 需保持错误链完整
- log.Fatal 仅用于启动阶段不可恢复的错误
- 业务错误与系统错误分离：业务错误返回 API 响应，系统错误记日志

【建议】
- 优先使用 errors.Is / errors.As 判断错误类型
- 定义模块级哨兵错误集中管理
```

标准错误处理模式：
```go
// models 层：记录 + 传递
func GetClient(id int64) (TClient, error) {
    var client TClient
    err := db.Get(&client, "SELECT * FROM t_client WHERE id = ?", id)
    if err != nil {
        if errors.Is(err, sql.ErrNoRows) {
            return TClient{}, fmt.Errorf("client %d: %w", id, ErrClientNotFound)
        }
        return TClient{}, fmt.Errorf("query client %d: %w", id, err)
    }
    return client, nil
}

// controllers 层：转换为 API 响应
func HandleGetClient(c *gin.Context) {
    id := c.QueryInt64("id")
    client, err := models.GetClient(id)
    if err != nil {
        if errors.Is(err, models.ErrClientNotFound) {
            api.Fail(c, "CLIENT_NOT_FOUND", "客户端不存在", nil)
            return
        }
        api.Fail(c, "INTERNAL_ERROR", "查询失败", nil)
        return
    }
    api.Success(c, client)
}
```

### 6.2 哨兵错误管理

```go
// 项目级哨兵错误集中声明
var (
    ErrClientNotFound = errors.New("client not found")
    ErrItemNotFound   = errors.New("item not found")
    ErrTaskNotFound   = errors.New("task not found")
    
    ErrTokenExpired   = errors.New("token expired")
    ErrTokenInvalid   = errors.New("token invalid")
)
```

### 6.3 前端错误处理

```
【强制】
- API 调用必须有 .catch 或 try/catch 兜底
- 业务错误由响应拦截器统一处理（401/403/5xx）
- 用户输入错误在组件内即时提示，不抛出全局异常
- 网络超时需明确提示用户重试
```

## 七、API 设计规范

### 7.1 统一响应格式

```
【强制】
所有 API 返回统一 JSON 结构：

{
    "code":    "200",       // 业务码（字符串）
    "message": "success",   // 描述信息
    "data":    { ... },     // 业务数据
    "traceId": "abc123"     // 链路追踪 ID（可选）
}
```

业务码对照：

| 业务码 | HTTP 状态 | 含义 |
|--------|----------|------|
| 200 | 200 | 成功 |
| 400 | 400 | 参数错误 |
| 401 | 401 | 未认证 |
| 403 | 403 | 权限不足 / CSRF |
| 404 | 404 | 资源不存在 |
| 429 | 429 | 限流 |
| 500 | 500 | 服务端异常 |

### 7.2 路由命名与版本管理

```
【强制】
- v1 接口保留在 /api/v1/*，至少一个大版本内兼容
- v2 接口统一前缀 /api/v2/*
- 路径使用 kebab-case 或 lowerCamelCase
- 使用名词复数或语义化动词：/v2/logs/search（POST）、/v2/logs/stream（GET）
- 不暴露内部实现细节：禁止 /queryTableList、/getUserInfoById 等 RPC 风格
- 路径参数用 :id / :taskNo / :traceId 占位
- MCP 工具名使用 snake_case：query_logs、search_similar、get_patterns
```

### 7.3 请求参数校验

```
【强制】
```

## 八、日志与可观测性

### 8.1 日志规范

```
【强制】
- 结构化日志使用 pkg/logger（基于 slog JSON 格式）
- 日志级别选择：
    - Debug：开发调试（生产不输出）
    - Info：关键业务节点（登录、注册、配置变更）
    - Warn：可恢复异常（降级、重试）
    - Error：不可恢复错误（需人工介入）
- 使用占位符而非字符串拼接：log.Info("client connected", "ip", clientIP)
- 禁止在日志中输出明文密码、Token、完整 Session ID

【建议】
- 关键操作日志使用统一前缀标签：[security]、[session]、[discovery]
- 一条日志只记录一件事
- 高并发路径避免 Debug 级别以上的日志
```

### 8.2 指标埋点

```
【建议】
- 接口维度：请求量（counter）、延迟（histogram）、错误率（counter）
- 业务维度：活跃客户端数、在线日志项数、搜索 QPS
- 使用 pkg/metrics 暴露 Prometheus 格式指标
- Metrics 端点不经过鉴权中间件（/metrics 公开）
```

### 8.3 链路追踪

```
【建议】
- 响应中携带 traceId 字段（由中间件自动生成或透传）
- 跨服务调用在 HTTP Header 中传递 X-Request-ID
```

## 九、安全编码规范

### 9.1 认证与会话

```
【强制】
- 密码存储使用 Argon2id（参数已在 auth 模块硬编码）
- JWT 使用 RS256 或 HS256+强密钥，禁用 none 算法
- Session Cookie 设置 HttpOnly + Secure + SameSite=Lax
- 登录接口必须限流：60 秒窗口内 ≤ 5 次失败，封禁 300 秒
- 生产模式禁止出厂默认密码启动
```

### 9.2 输入校验与注入防护

```
【强制】
- 所有外部输入必须校验（路径参数、Query、Body、Header）
- SQL 使用参数化查询（? 占位符），禁止字符串拼接
- 文件名/路径参数使用 sanitizeKey 白名单过滤：`^[a-zA-Z0-9._-]+$`
- 正则表达式限制执行时间，防止 ReDoS（设置超时或使用 RE2）
- CORS 白名单不得包含 *（生产环境）
```

### 9.3 数据安全

```
【强制】
- API 响应不暴露内部错误堆栈（生产环境）
- 敏感配置（密码、密钥）通过环境变量注入，不硬编码
- 数据库文件设置适当文件权限（仅属主可读写）
- 日志脱敏：不输出用户密码、Token 全文

【建议】
- 用户数据导出功能需审计日志
- 删除操作标记软删除而非直接物理删除
```

### 9.4 CSRF 防护

```
【强制】
- 非安全方法（POST/PUT/DELETE）必须携带 X-Requested-With 头
- 利用浏览器 CORS 策略阻止第三方站点设置自定义头
- GET/HEAD/OPTIONS 方法跳过 CSRF 校验
```

## 十、并发与性能

### 10.1 并发编程

```
【强制】
- 使用 sync.WaitGroup 等待 goroutine 完成，不依赖 time.Sleep 猜测
- 共享变量必须加锁保护（sync.Mutex 或 sync.RWMutex）
- goroutine 泄漏防护：使用 context.Context 传递取消信号
- 信号量限流替代无限制的 goroutine 创建

【建议】
- 数据库连接池设为写 1 / 读 N（避免写冲突，项目当前设为 1）
- SSE/Streaming 连接必须设置超时和断开清理
- 大文件读取使用 io.Pipe 或 bufio.Scanner，避免一次性加载
```

### 10.2 性能准则

```
【建议】
- SQLite 启用 WAL 模式（已配置）和 busy_timeout（已配置）
- 搜索/查询接口添加分页，禁止全量返回
- 频繁访问的数据使用内存缓存（ratelimit 的内存后端模式）
- 前端大列表使用虚拟滚动（日志搜索结果场景）
```

### 13.1 测试覆盖率

### 13.3 测试结构

```go
func TestSanitizeKey(t *testing.T) {
    tests := []struct {
        name    string
        input   string
        want    string
        wantErr bool
    }{
        {"valid plain", "simple_key-123", "simple_key-123", false},
        {"path traversal", "../../etc/passwd", "", true},
        {"empty", "", "", true},
    }
    
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := sanitizeKey(tt.input)
            if (err != nil) != tt.wantErr {
                t.Fatalf("sanitizeKey() error = %v, wantErr %v", err, tt.wantErr)
            }
            if got != tt.want {
                t.Errorf("sanitizeKey() = %q, want %q", got, tt.want)
            }
        })
    }
}
```

### 13.4 测试原则

```
【强制】
- 测试必须是幂等的（不依赖执行顺序）
- 临时资源使用 t.TempDir() + t.Cleanup() 管理
- 环境变量覆盖使用 t.Setenv()
- 集成测试使用 httptest.NewServer 或独立测试数据库
- 测试不应依赖外部网络/服务（外部依赖 Mock）

【建议】
- 单元测试与集成测试分离（Go 使用 build tag //go:build integration）
- 公共辅助函数提取到 _test.go 文件
- 关键安全路径（认证、限流、注入防护）必须有负面测试用例
```

```
【建议】
```
