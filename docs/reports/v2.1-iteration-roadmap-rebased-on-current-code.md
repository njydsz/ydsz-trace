## 三、对标 jlog / TLog 的差距定位

### 3.1 jlog 的三个必须借鉴的机制

| jlog 机制 | 本项目现状 | 差距性质 |
|---|---|---|
| 内存队列替代磁盘写 + Kafka，UDP 直推 Worker | logc 代理拉取文件，无 Agent 端队列 | **架构级**：高吞吐场景缺位 |
| Snappy/ZSTD 极致压缩，单机 1GB/s 原始日志 | 列式段存储有 gzip 但未启用 | **接线级**：能力已在，未挂载 |
| Client 动态获取 Worker 集群 + 负载均衡 | 单点服务，无集群发现 | **规模级**：多节点高可用缺位 |

### 3.2 TLog 的两个必须补上的能力

1. **日志框架层自动打标**：TLog 适配 log4j/log4j2/logback，通过字节码注入把 TraceId+SpanId+上下游追加进每条日志。本项目只在查询侧重建 trace，**采集侧无 TraceId 注入能力**——应补一个轻量 Go Agent SDK / 中间件，让业务方零侵入接入。
2. **异步线程 / 线程池 / 定时任务场景的上下文传递不中断**：TLog 明确覆盖这三类场景。Go 的 goroutine + context 传播机制天然不同，需要设计等效方案（`context.Context` 携带 traceID，跨 goroutine / channel / HTTP client 自动透传）。

### 3.3 不应盲从的部分

jlog 强依赖 ClickHouse 集群，TLog 只解决 traceId 一个点。本项目的差异化定位是**"轻量单二进制 + 内网私有化 + AI 智能漏斗"**（PRD §1.4）。**不应为对标而引入 ClickHouse/Kafka/HDFS 重型依赖**——那会直接违背 PRD §2.3"不牺牲 v1.x 核心竞争力：单二进制部署形态必须保留"。正确的借鉴方式是**取其机制、轻其形态**：用 Go channel+ring buffer 替代 Kafka、用已有列式段存储替代 ClickHouse、用单文件 SQLite 保持轻量。

## 五、执行建议：三条铁律

### 铁律一：先接线，再创新

当前最宝贵的资产是**一批已实现但未挂载的模块**（列式段存储、L2 embedding、RBAC 中间件、向量库）。V2.1 收尾批（16.5 人日）几乎不需要新算法，却能让系统的"已实现能力"真正对用户可见。**在没有接通这些之前投入 V2.3 的 Agent 研发，会让 Agent 建在一个半数能力空转的地基上。**

### 铁律二：AI 能力必须带评测门禁

PRD §2.3 明确"评测驱动上线：每个 AI 功能必须配套评测集与量化门槛，不达标不上线"。但当前 NL2DSL **评测集在 CI 中并未形成门禁**。建议 V2.1 收尾就把 FR-506（200 条中英文问句+标准 DSL）落地为 CI 阻断项——这是后续所有 LLM 能力的可信前提。

### 铁律三：轻量是护城河，不要用竞品的重量换对标

jlog 靠 ClickHouse 集群达成 1GB/s，TLog 靠字节码增强达成零侵入。本项目要赢的不是"更大吞吐"，而是**"1/10 资源达到 80% 能力 + 内网私有化 + AI 内建"**（PRD §1.4 表格结论）。因此借鉴路径应为：

- 学 jlog 的**机制**（内存队列、极致压缩、异步批量），用 Go channel + ring buffer + 已有 zstd 段存储实现，**不引入 Kafka/ClickHouse/HDFS**
- 学 TLog 的**采集端打标思路**，用 Go `context.Context` + 中间件实现跨 goroutine/HTTP 的 TraceId 透传，**不做字节码增强**
- 保持单二进制 + SQLite 的部署形态不动摇

## 七、一句话总结

**项目已经越过了"要不要做 AI"的阶段，进入了"把已有的 AI 地基接通"的阶段。** 后续版本的核心矛盾不是能力缺失，而是接线债务——V2.1 用 16.5 人日接通存量，V2.2 用采集/存储/异常补主干，V2.3 才轮到真正的 Agent 推理，V2.4 做生态开放。对标 jlog/TLog 时应学机制而非学重量，轻量私有化才是本产品不可替代的护城河。
