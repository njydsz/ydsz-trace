**关键发现**：sqlite.sql 与代码模型层 schema **已完全同步**（FR-308 已达标）。V2.1 新增的 AI/语义相关 7 张表均已在 schema 中建表但**未有业务逻辑写入**，属于"空表等待数据"状态。

### 1.2 表结构设计问题

**P0 问题**：

1. **时间字段使用 TEXT 格式**：部分时间字段使用 TEXT 存储（如 `created_time TEXT`），虽能做范围查询但效率不是最优。PRD FR-801 要求"基线学习按日周期"做聚合分析，TEXT 格式在大量数据时排序效率低于 INTEGER。

2. **JSON 字段未充分利用 SQLite JSON1 扩展**：`labels`/`symptoms` 等 JSON 字段以 TEXT 存储，无法直接利用 JSON_EXTRACT 做条件查询，按标签筛选需要额外解析。

3. **t_log_segment 缺少 template_id + seg_date 复合索引**：当前仅有 `(item_id, client_id, seg_date)` 索引。PRD FR-306 要求查询下推时，当查询带有 template_id 过滤条件时，无有效索引支持。

**P1 问题**：

4. **t_pattern_stat 时间桶粒度较粗**：PRD FR-304 要求"秒级聚合"，建议确认当前桶粒度是否满足场景，以及是否需要多粒度支持。

5. **向量索引大规模场景的存储选择**：当前 t_embedding 用 SQLite BLOB 存储向量，小数据量可行，但 PRD L2 层向量检索 P95 ≤ 1s 的目标下，大规模向量建议使用专用 HNSW 文件。

6. **t_trace_node 缺少服务维度的复合索引**：PRD FR-1004 要求"按服务维度的慢/错 TopN"，需评估是否需要 service 维度的复合索引。

### 1.3 数据库优化建议

| 优先级 | 建议 | 影响面 |
|--------|------|--------|
| P0 | 时间字段可统一为 INTEGER (unix ms) 以优化排序效率，应用层格式化输出 | 全模块读写路径 |
| P0 | 对 JSON 字段启用 SQLite JSON1 扩展，建立生成列索引（如 labels 中的 service） | client/alert 表 |
| P1 | t_log_segment 增加 `(template_id, seg_date)` 复合索引 | 检索下推路径 |
| P1 | 大规模向量场景考虑 HNSW 外存方案，SQLite 仅存元数据 | 语义检索路径 |
| P2 | t_pattern_stat 如果需要多粒度查询，可维护聚合视图或增加 bucket_sec 字段 | 异常检测 + 趋势图 |
| P2 | 大数据表（如 t_pattern_stat、t_trace_node）开启定期归档/分库策略 | 生命周期管理 |

## 四、架构优化分析

### 4.1 智能漏斗（L0-L3）落地评估

| 层级 | PRD 要求 | 当前状态 | 评估 |
|------|---------|---------|------|
| L0 规则层 | 正则、模板匹配、字段过滤 | pkg/parser/drain.go Drain 算法已嵌入 | ✅ 基本可用 |
| L1 统计层 | 基线、突变检测、TopN | pkg/stats/engine.go 已实现，Scanner 仅做规则告警 | ⚠️ 异常检测未完整集成 |
| L2 嵌入层 | 向量化、聚类、相似检索 | pkg/embedding + HNSW 已实现，但未嵌入写入流程 | ⚠️ 底层空闲 |
| L3 生成层 | NL2DSL、根因推理、报告 | NL2DSL 已实现（规则式），Agent 不存在 | ❌ 未实现 |

**核心差距**：智能漏斗的四层底层代码各有实现，但**没有在写入链路中联动形成自动流水线**。写入路径中 Drain 解析与 Embedding 计算解耦。

### 4.2 架构优化建议

**写入管线集成**：

| 阶段 | 现状 | 建议方案 |
|------|------|---------|
| 写入接收 | 仅写原始文本，不触发解析 | 增加 ParsePipeline：收到日志 → Drain 匹配/创建模板 → 字段抽取 |
| 向量化 | embedding 表有元数据但无数据 | 新增异步 Embedder：模板新增/变更时 → Encode → 存 t_embedding |
| 异常检测 | Scanner 仅在告警规则时运行 | 新增 AnomalyPipeline：pattern_stat 增量更新 → Z-Score → 写 t_anomaly_event |
| 列式化 | t_log_segment 表存在但空 | 新增 SegmentWriter：按小时聚合 → 压缩 → 写 t_log_segment |

**模块解耦**：

| 当前 | 建议 |
|------|------|
| 逻辑集中在单服务 | 按 PRD 七层架构拆分为独立 goroutine/进程 |
| 控制器直接访问 *sqlx.DB 全局变量 | 引入 Repository 接口层，便于 mock 测试 |
| pkg/embedding 混合计算与存储 | 拆分为 compute + store 子模块 |

## 十、总结

Ydsz Trace V2.1 的工程落地**基础设施扎实但业务贯通不足**：

**基础设施（✅）**：15 张表已同步、统一响应包就绪、SSE 安全封装独立、JWT 字段扩充

**贯通集成（⚠️）**：AI 四层漏斗底层代码存在但写入路径未串联，前端 NL2DSL 先行但语义检索无入口

**测试覆盖（❌）**：Go ~55-60% / 前端 ~15-20%，距 PRD 目标差距显著

**生产化安全（⚠️）**：注册无鉴权、JWT aud/nbf 验证待确认、审计日志未全量覆盖

建议 V2.1 以"安全 + 工程规范 + 体验"为三大抓手，补齐 P0 后快速推进 V2.2 写入管线集成。
