# 云顶追踪 v2.1 PRD 落地现状与后续优化建议（2026-10-29）

> 基准：`docs/Ydsz_Trace_AI时代的日志检索分析引擎_PRD_V2.1.md`
> 分析对象：前后端最新代码（截至 2026-10-29）
> 目标：从数据库表、接口测试、前后贯通、架构优化、功能增强、性能提升、体验改善等维度，输出可落地的后续优化建议

## 一、当前落地的总体判断

相比 2026-10-13 的差距报告，当前代码已完成大量 V2.1 基础设施搭建：

- 数据库层：15+ 张 v2 表已建（t_log_template、t_embedding、t_anomaly_event、t_trace_node、t_case_library、t_audit_log、t_user、t_user_binding、t_log_segment、t_model_capability、t_pattern_stat 等），schema 同步机制（`sqls/sqlite.sql` + `models/def.go` 程序化建表 + 增量列迁移）已就绪。
- 后端 API：NL2DSL、语义检索、traceId 聚合/瀑布视图、SSE 流式搜索/tail、告警规则 CRUD、模型能力 CRUD、审计日志、用户管理、用户绑定、日志段存储等端点全部挂载。
- 前端页面：对话式工作台、经典检索、实时日志、告警管理、链路追踪、洞察看板、模型管理、全局搜索、骨架屏、主题切换、快捷键等 10 个核心页面均已实现。
- 公共库：Drain 解析、DSL 引擎、向量化（本地/云端）、统计引擎、脱敏、JWT+RBAC、sanitize、缓存、metrics、数据源（File/Docker/K8s）等 pkg 全部可用。

**但存在一个根本性结构问题：v2 的"写入管线"（L0→L1→L2→L3）完全未接通。** 所有 v2 表都只有读取路径或手工写入路径，没有自动化的采集→解析→统计→向量化→段存储流水线。这导致：

- `t_log_template`、`t_embedding` 恒空 → 语义检索永远返回空
- `t_pattern_stat` 无自动写入 → 异常检测基线永不更新 → 智能告警不可用
- `t_log_segment` 无自动写入 → 段存储引擎形同虚设
- `t_trace_node` 仅 trace 查询时写入，非自动链路重建

### 2.2 关键缺口

1. **t_log_template 无写入方法**：`models/semantic_search.go` 只有 `GetTemplateByID` 和 `SearchTemplates`，没有 `InsertTemplate` 或 `UpsertTemplate`。所有模板数据依赖手工 SQL 或外部导入，Drain 解析结果不会自动落库。

2. **t_embedding 无写入方法**：`models/semantic_search.go` 只有 `GetEmbeddingByKey`，没有 `StoreEmbedding`。`pkg/embedding.SQLStore` 有 `Store` 方法但全项目零调用。

3. **t_conversation / t_conversation_msg 未建表**：对话式工作台的消息仅存内存，刷新即丢失。PRD FR-901 要求"会话内 5 轮追问上下文不丢失"，当前无法满足。

4. **t_user_binding 中间件未注册**：`AccessControlMiddleware` 已在 `models/user_binding.go` 中实现，但 `routers/router.go` 未将其加入鉴权链。行级 RBAC 实际不生效。

5. **sqls/sqlite.sql 用 DROP TABLE**：与 `models/def.go` 的 `IF NOT EXISTS` 语义不一致，新环境初始化时如果先跑 sqlite.sql 再跑 def.go 的迁移，可能丢数据。

### 2.3 落地建议

| 优先级 | 建议 | 具体行动 |
|---|---|---|
| P0 | 补全模板写入链路 | 在 `models/semantic_search.go` 新增 `UpsertTemplate(template)` 方法；在 `services/services.go` 的 `ParserService.ParseLine` 返回后自动 upsert 到 t_log_template |
| P0 | 补全向量写入链路 | 在 `models/semantic_search.go` 新增 `StoreEmbedding(targetType, targetID, vector, modelVersion)` 方法；在模板 upsert 后异步调用 `embedder.Embed` + `store.Store` |
| P0 | 建 t_conversation / t_conversation_msg 表 | 按 PRD 7.1 字段设计，在 `models/def.go` 程序化建表；新增 `models/conversation.go` CRUD |
| P1 | 注册 AccessControlMiddleware | 在 `routers/router.go` 的 `v2 := r.Group("/api/v2", auth)` 链中加入 `models.AccessControlMiddleware()`，对 /items 和 /logs 启用行级过滤 |
| P1 | 统一 schema 初始化 | 废弃 `sqls/sqlite.sql` 的 DROP TABLE 语句，改为 `CREATE TABLE IF NOT EXISTS`；或仅在全新环境使用，迁移环境只跑 def.go |

## 五、架构优化维度

### 5.1 当前架构问题

1. **全局 DB 单例**：`models.DB` 是全局变量，`MaxOpenConns(1)`，无依赖注入，测试无法替换。所有控制器直接引用 `models.DB`，耦合度高。

2. **services 包是死代码**：`logs/services/services.go` 中的 `ParserService`、`AnomalyService`、`ClusterService` 无任何控制器调用方。模板归一化逻辑在 `services.go`、`search.go`、`stream.go` 三处重复实现（`normalizeLine`/`hashTemplate`/`extractTemplateFields` 各一份）。

3. **pkg/dsl 是孤岛**：完整的词法/语法/编译引擎零调用。查询链路仍走 NL2DSL 正则 + `source.CompileQuery` 双轨，DSL 引擎未接入主链路。

4. **pkg/mask 是孤岛**：7 种脱敏策略全项目零调用。FR-1303 要求"敏感字段检出率 ≥ 98%"，但展示层和外发层均未接入脱敏。

5. **logc 无 pipeline/index**：PRD 规划的端侧 ParsePipeline/EmbedPipeline/AnomalyPipeline/SegmentWriter/本地索引全部为空目录。logc 仅做文件读取和转发，不做任何解析/统计/向量化。

6. **写入路径未接通**：v2 的 L0→L1→L2→L3 四层智能调用策略（PRD 6.2）完全未实现。当前只有 L0 规则层（NL2DSL 正则）可用，L1/L2/L3 层虽有算法但无数据供给。

7. **logc 注册签名 bug**：`logc/controllers/register/register.go` 中 `computeHMAC(vKey, vKey, timestamp)` 将 secret 和 vkey 传同值，与服务端 `verifyHMACSignature(secret=registerKey, vkey)` 不一致，导致签名校验必失败、降级明文。

8. **logc 无鉴权中间件**：logc 仅监听 127.0.0.1，但无鉴权中间件，任何本地进程都可调用其 API。

9. **SSE 端点无心跳**：`/logs/tail` 和 `/logs/stream` 无心跳机制，长时间无数据时客户端无法区分"连接正常但无数据"与"连接已断"。

10. **前端路由无懒加载**：`router/index.js` 所有 views 顶层 import，首屏加载全部 chunk。

### 5.2 落地建议

| 优先级 | 建议 | 具体行动 |
|---|---|---|
| P0 | 引入写入管线 | 在 logc 或 logs 侧新增 BackgroundPipeline：定时扫描新日志 → Drain 解析 → upsert t_log_template → 异步 embed → upsert t_embedding → 更新 t_pattern_stat → 触发 AnomalyEngine → 写入 t_anomaly_event |
| P0 | 修复 logc 注册签名 | `register.go` 中 `computeHMAC` 的 secret 参数改为真正的 register_key（非 vkey），与服务端 `client.go` 的 `verifyHMACSignature` 对齐 |
| P0 | 接入 pkg/mask | 在 `logs/controllers/logs/search.go` 的 `buildRow` 和 `buildHit` 中对 content 字段执行 `mask.MaskAll`；在 `logc/controllers/file/file.go` 的 Query 返回前执行外发脱敏 |
| P1 | 接入 pkg/dsl | 在 NL2DSL 解析器中增加 DSL 解析路径：用户输入先尝试 `dsl.Parse`，失败再走正则 NL2DSL；或在 /logs/search 的 `query` 字段中优先使用 DSL 编译器 |
| P1 | 消除 services 重复 | 将 `services.go` 的 `ParserService`/`ClusterService` 接入 search.go 和 stream.go，删除三处重复的 `normalizeLine`/`hashTemplate`/`extractTemplateFields` |
| P1 | DB 依赖注入 | 定义 `Store` 接口（含常用 CRUD），`models.DB` 改为 `Store` 实现，控制器通过接口引用；测试时注入 mock |
| P1 | logc 鉴权 | 在 `logc/routers/router.go` 中加入本地 Token 中间件（env `YDSZ_LOGC_TOKEN`），所有端点校验 |
| P2 | SSE 心跳 | 在 `stream.go` 的 Tail 端点每 15s 推送 `event: ping`；前端 `sse.js` 收到 ping 重置超时计时器 |
| P2 | 前端路由懒加载 | `router/index.js` 所有 views 改为 `() => import(...)` |
| P2 | 统一 API 响应 | 将 `api.Success(c, msg, Page)` 包装 Page 结构的调用改为 `api.Paginated(c, msg, page.List, page.Total)`，消除过渡期兼容代码 |

### 6.2 根因分析 Agent MVP 建议

PRD FR-901~908 是 v2.1 的核心卖点，但实现复杂度极高。建议 MVP 路径：

1. **工具集**：先实现 4 个只读工具（search_logs、agg_stats、get_context、get_trace），复用现有 API。
2. **编排**：用 Go 实现 ReAct 循环（最大 8 步），每步调用 LLM（本地 7B 或云端）生成工具调用 JSON，执行后将结果追加到上下文。
3. **输出**：三段式（假设→验证→结论），结论中引用证据 ID（模板 hash + 行号）。
4. **降级**：LLM 不可用时退化为"统计结论"（基于 AnomalyEngine + TopPatterns 直接生成文本）。
5. **会话**：t_conversation 存储每轮对话，支持 5 轮上下文。

### 6.3 告警增强建议

当前告警仅支持 Webhook 单渠道，且扫描器依赖 `patternStats` 表（该表无自动写入）。建议：

1. **扫描器增强**：除 patternStats 外，增加实时扫描模式——对 SSE tail 的日志流做滑动窗口计数，触发阈值立即告警。
2. **五渠道**：在 `alert/delivery.go` 中抽象 `Notifier` 接口，实现 Webhook/WeCom/DingTalk/Feishu/Email 五个实现。
3. **聚合降噪**：在 `alert/scanner.go` 中增加聚合窗口（默认 5min），同模板多次触发合并为一条告警，附带首次/最近/计数。
4. **一键诊断**：告警卡片增加"AI 诊断"按钮，跳转 `/conversation?alertId=xxx`，对话工作台读取告警上下文预填首轮问题。
